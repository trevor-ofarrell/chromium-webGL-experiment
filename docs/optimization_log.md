# Optimization Log

Date: 2026-05-22

This log records the final decision state for the Chromium-derived Three.js viewer runtime at Chromium revision `3a94d90ec3c04556622c56944796dd76753e0581` and current fork revision `3a94d90ec3c04556622c56944796dd76753e0581+viewerpatch-43dbf0b6871e`.

Measured performance rows from earlier artifacts remain historical until the current patch-series revision is rebuilt after the WDAC/Application Control blocker clears.

Allowed final optimization statuses are `kept`, `reverted`, `blocked`, or `not useful`.

Primary evidence:

- Official manifest: `benchmarks/reports/official-comparison-manifest.json`
- WebGL2 report: `benchmarks/reports/official-webgl2-comparison.md`
- WebGPU report: `benchmarks/reports/official-webgpu-comparison.md`
- Trusted matrix manifest: `benchmarks/reports/trusted-experiment-matrix-manifest.json`
- Trusted WebGL2 report: `benchmarks/reports/trusted-experiment-matrix-webgl2-comparison.md`
- Stability artifacts: `benchmarks/raw/baseline-content-shell-long-stability-instancing-webgl2.json`, `benchmarks/raw/fork-viewer-default-long-stability-instancing-webgl2.json`
- Runtime target: Chromium `content_shell`

Official WebGL2 default fork results versus stock content shell: package size -130.3 MB, average startup -220 ms across the scene suite, average FPS -1.3%, average p99 frame time -28.8 ms, average CPU frame time -0.06 ms, and average render submission -0.05 ms. Official WebGPU default fork results versus stock content shell: package size -130.3 MB, average startup -12 ms, average RSS -15.3 MB, average FPS -24.6%, and average p99 frame time +135.9 ms. WebGPU GPU timestamp timing is disabled in official WebGPU evidence because timestamp queries caused device loss during stress runs; adapter/device metadata remains captured.

Follow-up iteration on 2026-05-21 tightened performance evidence validation so WebGPU device loss, WebGL context loss, and render errors are rejected by suite and strict official comparison gates. The low-level benchmark runner now derives checkout-built fork result metadata from the Chromium revision plus the full viewer patch-series hash when `--forkRevision` is not explicitly supplied, preventing stale Chromium-only or incomplete-patch fork stamps from entering strict reports. The earlier aggressive WebGPU shader-heavy speedup is no longer considered valid evidence because the underlying run recorded WebGPU device loss. Short safe-window iteration checks are recorded in `docs/performance_iteration_2026-05-21.md`.

Follow-up hardening on 2026-05-24 made WebGPU device-loss detection independent of Three.js callback forwarding by subscribing directly to `GPUDevice.lost` and recording `webgpu_device_loss_source` in benchmark JSON. This does not create a speedup by itself; it reduces the risk that a contaminated WebGPU run can pass the speed-claim filters.

The latest complexity-2 iteration found a WebGL2 zero-copy-only candidate (`--viewer-zero-copy`, aliasing Chromium `--enable-zero-copy`) that improved full-suite average FPS by +0.7% versus stock content_shell and reduced average CPU, render submission, dropped frames, and startup time. It is not yet retained as the default WebGL2 profile because average 1% low, 0.1% low, p95, and p99 regressed. WebGL2 relaxed validation alone regressed -7.7% on complexity-2 draw-call stress, and relaxed validation plus ANGLE Vulkan was invalid due WebGL context loss.

The current WebGPU process candidates remain insufficient for a retained full-suite speedup. Trusted single-process with GPU timing disabled improved many-draw-calls and glTF-loader stress but the full seven-scene complexity-2 suite averaged only +0.1% FPS, with average 1% low, 0.1% low, p95, and max-frame regressions despite large RSS/startup wins. The default viewer profile improved texture-streaming tails but averaged -0.2% FPS across the full suite. In-process GPU improved the decisive draw-call/glTF/texture subset by +3.7% on average but regressed texture-streaming by -18.4%, so it was not expanded to full-suite retention. WebGPU zero-copy did not fix texture-streaming average FPS and is rejected as a default profile for now.

Additional texture upload attribution added `textureUploadMode=data` to the viewer and benchmark runner. The DataTexture path increased absolute texture-streaming throughput, but it did not create a retained fork speedup: stock WebGPU measured 78.7 FPS, fork default 78.2 FPS, and fork single-process 70.2 FPS. Dawn `skip_validation` worsened the same DataTexture probe, and WebGL2 zero-copy on DataTexture texture-streaming regressed average FPS by 2.0%.
